# Models, validators, and migrations

## Models and validators

- The `# == Schema Information` header is generated by `annotate_rb` after
  `db:migrate` in development (`lib/tasks/annotate_rb.rake`). Don't hand-edit
  it; run the migration and let it regenerate.
- Primary keys are UUIDv4 (`gen_random_uuid()`), and no model sets
  `implicit_order_column` any more — `ImplicitOrderingChecker` is switched off
  in `.database_consistency.yml`. Nothing recovers a chronological order for
  you: `first`, `last` and every Pagy page order by a random UUID, which is
  arbitrary and not even stable between two runs of the same query. Any scope,
  query or index action whose order matters must call `.order(...)` itself —
  `Crudable#index` paginates whatever scope it is handed without adding one,
  and an unordered paginated list can repeat a row on page 2 and drop another
  entirely.
- Enums go through `enumerize`, not Rails' native `enum` — this app does not
  use the native one. Follow `User#provider`: `extend Enumerize` once, then
  `enumerize :column, in: { key: 0, ... }, default: :key, scope: true` with
  explicit integer values.
- Shared magic values (content-type allowlists, size limits, regexes) live in
  `Constants` (`Constants::IMAGE_CONTENT_TYPES`, `Constants::PASSWORD_REGEX`),
  not hardcoded again in the model or validator that needs them.
- Callbacks are for normalization and defaults only (`before_validation`,
  `after_initialize`). A callback that sends mail, enqueues a job, calls an
  API, or creates a related record is a workflow — it belongs in an
  Operation (`app/operations`), not a callback. See "Where logic goes" in
  `rails-architecture.md`.
- A validation that promises an invariant (`presence`, `uniqueness`) needs the
  matching database constraint (`null: false`, a unique index) — a model-only
  promise is a race, not a guarantee. `database_consistency` checks this.
- Any model reachable through Ransack search must declare
  `ransackable_attributes` and `ransackable_associations` explicitly (Ransack
  4.x has no default allowlist). Default `ransackable_associations` to `[]`
  unless a search genuinely needs to reach across a join, as `User` does —
  every attribute and association you add to these lists is filterable by
  anyone who can reach the search params.

## Custom validators (`app/validators`)

Subclass `ActiveModel::EachValidator`. Return early on a blank value unless
blank itself is the violation. Route the message through `I18n.t(...)`
(`config/locales/en.yml`) rather than a literal string — see
`PasswordValidator`.

## Migrations (`db/migrate`, `db/schema.rb`)

`strong_migrations` and `good_migrations` are both active. Assume every table
can be large in a real deployment built from this template.

`config/initializers/strong_migrations.rb` sets `start_after = 20241004100359`
and `target_version = '16'` (the PostgreSQL version the gem judges safety
against). That marker matters for the squash workflow below: every migration in
the repo today is at or before it, so editing one gets **no** check from the
gem — the reasoning about locks, rewrites and backfills is yours to do by hand
there. A migration added after the marker is checked normally. Bump
`start_after` only when history is squashed again, never to silence a warning.

- Never reference an application model from a migration — `good_migrations`
  blocks it, and the model will not match the schema at that point in history.
- Adding an index to an existing table needs `disable_ddl_transaction!` plus
  `algorithm: :concurrently`. Inside `create_table` no such dance is needed.
- Split schema changes from large data backfills into separate migrations.
- Avoid table rewrites and long exclusive locks (changing a column type, adding
  a `NOT NULL` column with a default on a large table).
- Add foreign keys and database constraints where the model already promises the
  invariant. A model-level `validates ... uniqueness` without a matching unique
  index is a race, not a guarantee — `database_consistency` will report it.
- New tables take `id: :uuid` like the existing ones. The models do not set
  `implicit_order_column`, so the ordering caveat in the Models section applies
  to every table you add.
- A unique index over a nullable column does not constrain the rows where that
  column is `NULL` — in Postgres every `NULL` is distinct, so duplicates slip
  through. Pass `nulls_not_distinct: true` (PG 15+) when those rows must be
  unique too. `index_roles_on_name_and_resource_type_and_resource_id` does,
  because a global role has no `resource` and two `super_admin` rows would
  otherwise both be legal.

### This template squashes history

Migration history here is intentionally collapsed into the original files rather
than appended to, because the template ships no production data. When changing
the schema, edit the original `create_table` migration, then regenerate:

```sh
rm db/schema.rb && RAILS_ENV=test bin/rails db:drop db:create db:migrate
```

This is the opposite of the rule for a deployed application — do not carry this
habit into one.
